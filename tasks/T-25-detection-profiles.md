## Почему задача появилась

Сверка отчёта о качестве с кодом (`docs/spec/QUALITY.md` §9) шла через прогоны
под разными профилями. Прогон под `strict` совпал с прогоном под `balanced`
побайтово — вплоть до списка пропущенных значений: сокрытие 0,9752, точность
0,9996, две сработавшие ловушки из 144 в обоих случаях.

Причина в `internal/detect/engine.go`:

- `admits` допускает кандидата от уровня `Strong` и в `Strict`, и в `Balanced`
  — ветки различаются только записью, но не условием;
- подъём по кластеру `promoteByCluster` переводит слабого кандидата в `Strong`
  **до** отбора и выключен только у `Paranoid`.

Значит слабый кандидат внутри кластера проходит и под `strict` — ровно то
поведение, которое README приписывал одному `balanced`. Описание в README
поправлено сразу: описывать несуществующее различие нельзя. Сам разбор
поведения — здесь.

Тестов на профиль `strict` в пакете нет ни одного, `engine.go` вообще не имеет
своего файла тестов.

## Что решить до правки

Это не опечатка, а выбор семантики, и он влияет на качество защиты:

1. **`strict` = без подъёма по кластеру.** Тогда `promoteByCluster` вызывается
   только для `Balanced`. Поведение совпадает с README и с комментарием в
   `config.yaml`. Цена — прогон качества под `strict` даст меньшее сокрытие;
   насколько меньше, покажет замер.
2. **`strict` = только `Certain`.** Ближе к букве «только достоверные», но
   отсекает и сильных кандидатов с явным маркером типа рядом; для профиля,
   который кто-то включит ради меньшего числа ложных срабатываний, это скорее
   всего слишком грубо.
3. **Отказаться от `strict`.** Оставить два профиля и убрать третье имя из
   конфигурации, README и `ParseProfile`. Честнее, чем держать настройку,
   которая ничего не меняет, но отнимает у потребителя рычаг.

Вариант 1 выглядит предпочтительным: он совпадает с уже написанным описанием
и не трогает контракт конфигурации.

## Чего делать нельзя

- Менять профиль потребителя `benchmark`: контракт автопроверки обслуживается
  им, и на нём измерено всё содержимое `docs/spec/QUALITY.md`.
- Объявлять новое поведение `strict`, не прогнав качество под ним. Числа в
  отчёте помечаются `RESULT` только после измерения (AGENTS.md §9).
