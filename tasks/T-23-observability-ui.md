## Цель

Сейчас стенд разбирает один запрос и забывает его. Журнал уходит в `stdout`,
и на демонстрации его приходится показывать переключением в терминал.
Трассировки нет вовсе.

Надо, чтобы жюри видело на одной странице: поток журнала, историю запросов с
возможностью открыть любой, разбор маскирования по типам ПД и трассировку
этапов обработки.

Это закрывает критерий «Безопасность, логирование и метрики» целиком и
заметно усиливает критерий «Качество демо».

## Главный инвариант

Ни история, ни журнал на странице, ни трассировка **не содержат значений
персональных данных**. Хранятся и показываются: идентификатор запроса,
потребитель, операция, имена типов ПД, счётчики по типам, длительности,
исход. Значения — никогда. Это REQ-701, и он важнее любой наглядности.

Тест на утечки из `internal/obs/leak_test.go` обязан быть расширен на новые
поверхности: буфер истории, поток журнала и трассировка проверяются наравне
с уже проверенными журналом, метриками и телами ответов. Поиск ведётся по
каждому значению отдельно — сравнение целых строк пропустит частичную утечку.

## Что сделать

### 1. Буфер истории запросов — `internal/obs/recorder.go`

Кольцевой буфер фиксированного размера. Запись содержит: идентификатор
запроса, момент, эндпоинт, операцию, потребителя, множество найденных типов
и счётчики по ним, множество замаскированных типов и счётчики, длительности
по этапам, исход, признак безопасного отката.

Требования:

- Размер ограничен настройкой, по умолчанию 200 записей. Неограниченного
  роста быть не должно.
- Запись не аллоцирует: структура фиксированного размера, множества типов —
  битовые маски, счётчики — массив.
- Запись безопасна для конкурентного доступа и не тормозит горячий путь.
  Сервис держит 20 тысяч запросов в секунду; проверь бенчмарком, что запись
  в буфер не ухудшает это заметно. Если ухудшает — предусмотри выключение
  настройкой и объясни цену в комментарии.
- Буфер выключается настройкой целиком.

### 2. Трассировка этапов — `internal/obs/tracer.go`

Собственная, в памяти, без внешних зависимостей и без OpenTelemetry.

Запрос — это дерево отрезков: приём и разбор, детекция, применение политики,
маскирование, запись соответствия, ожидание модели, восстановление, запись
ответа. У каждого отрезка имя, начало относительно старта запроса и
длительность.

Ожидание модели помечается отдельно как **не входящее во время сервиса**:
организаторы измеряют только наше время, и на странице это должно быть видно
без пояснений.

Трассировка привязывается к записи истории по идентификатору запроса.

### 3. Страница — `web/index.html`

Добавь к существующим разделам:

- **Поток журнала.** Последние записи с фильтром по уровню, типу ПД и исходу.
  Обновление без перезагрузки страницы. Способ выбери сам: периодический
  опрос проще и надёжнее потока событий, решение обоснуй комментарием.
- **История запросов.** Таблица последних запросов: время, идентификатор,
  потребитель, операция, найденные типы, длительность, исход. Щелчок по
  строке открывает разбор этого запроса.
- **Трассировка.** Отрезки на временной шкале для выбранного запроса.
  Ожидание модели визуально отделено от времени сервиса.
- **Метрики.** Latency, RPS и TPS, снятые с `/metrics`. Это прямое требование
  ТЗ §3.2.4, и сейчас их видно только текстом в формате Prometheus.

Ограничения прежние: без сборки фронтенда, без внешних ссылок, встраивание
через `//go:embed`, интерфейс на русском, крупный шрифт и высокий контраст
для демонстрации экрана.

### 4. Эндпоинты

Новые эндпоинты требуют ключ, как и остальные продуктовые. Исключение —
только сама страница по `GET /`.

Продумай, не станет ли поток журнала способом обойти изоляцию потребителей:
записи одного потребителя не должны быть видны другому. Если полноценная
изоляция усложняет непропорционально — ограничь доступ к журналу и истории
отдельным правом в политике потребителя и объясни решение.

  **Что добавлено.** `internal/obs/recorder.go` — два кольцевых буфера
  фиксированного размера: история запросов (200 записей) и поток журнала
  (500 записей), плюс `slog.Handler`-зеркало, которое переносит записи
  настоящего журнала в буфер по **белому списку имён атрибутов**.
  `internal/obs/tracer.go` — собственная трассировка: девять перечислимых
  этапов деревом в два уровня (приём, защита → детекция/политика/
  маскирование/запись соответствия, ожидание модели, восстановление, запись
  ответа), отрезок = смещение от старта плюс длительность, без указателей.
  Транспорт (`process.go`, `proxy.go`, `ui.go`) собирает трассировку на стеке
  обработчика и пишет запись **после** отправки ответа. Ядро
  (`gateway.go`, `process.go`, `proxy.go`) отдаёт длительности этапов полями
  `DetectNs`/`PolicyNs`/`MaskNs`/`StoreNs`/`RestoreNs`. Три новых эндпоинта:
  `GET /api/v1/ui/history`, `/api/v1/ui/trace?id=`, `/api/v1/ui/journal?after=`.
  На странице — четыре блока: метрики (Latency avg и p95, RPS, TPS, ожидание
  модели), поток журнала с фильтрами по уровню/типу ПД/исходу, история
  запросов и трассировка.

  **Инвариант приватности.** Ни значения, ни исходный текст в буферы не
  попадают по построению: запись истории состоит из чисел, перечислимых
  меток и битовых масок типов — строкового поля для текста в ней нет; журнал
  читает только разрешённые имена атрибутов, и каждое разрешённое имя несёт
  значение из реестра `internal/pii`, из конфигурации или измеренное самим
  сервисом. `payload_id` в поток журнала на странице сознательно не попадает:
  его значение задаёт клиент, а перечень REQ-700 для стенда его не требует.
  Дополнительно `sanitizeRequestID` в middleware ограничивает единственное
  строковое поле, на которое влияет клиент (заголовок `X-Request-Id`):
  64 байта и только `[A-Za-z0-9_.:-]`, иначе выдаётся собственный
  идентификатор.

  **Изоляция потребителей — полная, без нового права в политике.** Отдельное
  право не понадобилось: достаточно сравнения идентификаторов, поэтому выбран
  строгий вариант. Каждая запись несёт владельца (`owner` — предъявитель
  ключа) отдельно от показываемого потребителя (`consumer` — чья политика
  применена). Это важно для стенда: прогон под чужой политикой принадлежит
  жюри, а не владельцу политики. Правило видимости одно на историю и журнал:
  запись по ключу видна только владельцу ключа; запись без владельца —
  служебная. Записи `POST /process` владельца не имеют, но называют
  потребителя `benchmark`: контур по требованию организаторов работает без
  аутентификации, его телеметрия публична по построению, и скрывать её не от
  кого. У записей без владельца и без потребителя (отказ по перегрузке,
  паника — они делаются до аутентификации) идентификатор запроса при выдаче
  снимается: он мог принадлежать чужому обращению. `internal/policy`
  не правился.

  **Способ обновления — периодический опрос раз в 2 с, не поток событий.**
  SSE держал бы по открытому соединению на зрителя, занимая слот
  `max_concurrent` на всю демонстрацию, и требовал бы heartbeat,
  переподключения и горутины с условием выхода на подписчика. Опрос не хранит
  состояния на сервере, переживает перезагрузку страницы и потерю сети и не
  может заклинить ограничитель. Журнал опрашивается разностно (`after=<seq>`).

  **Настройка.** Поля в `internal/config/schema.go` нет — файл вне `owns`.
  Размеры взяты константами `DefaultHistorySize = 200` и
  `DefaultJournalSize = 500` (обоснование — в комментариях), выключение —
  переменной окружения `AIGW_OBS_BUFFERS=off`, которая выключает историю,
  журнал и трассировку целиком. **Оркестратору:** предлагается секция
  `observability` в `File`:

  ```go
  // ObservabilitySection — буферы наблюдаемости демонстрационного стенда.
  type ObservabilitySection struct {
      // Enabled включает историю, поток журнала и трассировку. По умолчанию true.
      Enabled *bool `yaml:"enabled"`
      // HistorySize — вместимость кольцевого буфера истории, по умолчанию 200.
      HistorySize int `yaml:"history_size"`
      // JournalSize — вместимость кольцевого буфера журнала, по умолчанию 500.
      JournalSize int `yaml:"journal_size"`
  }
  ```

  Подключается одной строкой в `httpapi.NewServer`: вместо
  `obs.NewRecorderFromEnv()` — `obs.NewRecorder(snap.Observability.HistorySize,
  snap.Observability.JournalSize)`; выключение — нулевые размеры.

  **Бенчмарк, цифры (RESULT).** `go test -run '^$' -bench 'Recorder|Record'
  -benchmem -benchtime=3s ./internal/obs`, Apple M1 Max, darwin/arm64:

  | Бенчмарк | до | после | 0 аллокаций |

  | `Recorder.Record`, последовательно | 2,05 нс/оп (выключен) | 14,57 нс/оп | да |
  | `Recorder.Record`, `-parallelism 200` | 0,29 нс/оп (выключен) | 106,8 нс/оп | да |
  | запись `slog` с зеркалом журнала | 1181 нс/оп | 1320 нс/оп | да, 3 аллокации у обоих — они принадлежат `slog` |

  **Осталось незакрытым.**

  - Настройка живёт в переменной окружения, а не в `config.yaml`: поле схемы

    контура `/v1/*` этого перекоса нет; разносить их на отдельные этапы

  - Длительность родительского отрезка «Защита запроса» на продуктовом
    контуре получается вычитанием (`всего − ожидание модели − восстановление`),

    виден всем. Считаю это телеметрией сервиса, а не данными потребителя;
    если оркестратор решит иначе — прятать их нужно отдельным правом, а это
    правка `internal/policy`.

    цена записи в буфер бенчмарком. Полный прогон — за `load-test`.
