## Цель

Довести наблюдаемость до состояния, в котором жюри может увидеть Latency, RPS
и TPS по критерию 6, и доказать тестами, что персональные данные не утекают
в журнал, метрики и тела ошибок.

## Что уже есть

`internal/obs/metrics.go` и `internal/obs/log.go` реализованы: гистограммы с
фиксированными границами, счётчики по перечислимым меткам, экспозиция в
формате Prometheus, журнал на `slog`. `internal/httpapi/middleware.go`
ограничивает одновременную обработку и отвечает 429 с `Retry-After`.

Эти файлы **не трогать** — задача в том, чтобы покрыть их проверками и
закрыть найденные пробелы через свои файлы. Нашёл дефект в чужом файле —
это блокер для оркестратора, а не повод править.

## Что сделать

### `metrics_test.go`

- Экспозиция разбирается как корректный текстовый формат Prometheus:
  для каждой метрики есть строки `# HELP` и `# TYPE`, значения числовые.
- Гистограмма: кумулятивность корзин не нарушается, `_count` равен числу
  наблюдений, `_sum` соответствует сумме, корзина `+Inf` содержит всё.
- Наблюдение за границами сетки (0 и очень большое значение) попадает
  в нужные корзины.
- Метки перечислимы: невозможно зарегистрировать произвольную метку.
  Проверяется тем, что API принимает только значения типов `Endpoint`, `Op`,
  `Outcome`, `pii.Type`.
- Конкурентные наблюдения из нескольких горутин не теряются
  (`go test -race`, сверка итогового `_count`).

### `log_test.go`

- Уровни `debug`, `info`, `warn`, `error` и форматы `json`, `text`
  разбираются; неизвестное значение даёт ошибку с внятным текстом.
- Запись в формате `json` разбирается как корректный JSON.
- `LoggerFrom` на контексте без журнала возвращает работающий журнал,
  а не nil.

### `leak_test.go` — проверка на утечки

Ключевой тест задачи. Берётся набор размеченных синтетических значений всех
типов ПД. Выполняется полный цикл: запрос на `/process`, запрос с невалидным
телом, запрос без `payload_id`, запрос с телом сверх лимита. Журнал пишется
в буфер, метрики снимаются с `/metrics`.

Затем по **каждому** размеченному значению выполняется поиск в трёх местах:
накопленный журнал, тело `/metrics`, тела всех ответов. Ни одно значение
не должно найтись.

Сравнение целого payload не годится — оно пропустит частичную утечку.
Проверять надо каждое значение по отдельности.

Дополнительно проверить, что в метках метрик нет `payload_id`: их присутствие
означало бы неограниченную кардинальность.

### `middleware_test.go`

- При исчерпании предела одновременной обработки возвращается 429
  с непустым `Retry-After`, а не таймаут и не 500.
- После освобождения места запросы снова обслуживаются.
- Паника в обработчике превращается в 500, сервер продолжает работать,
  тело ответа не содержит текста паники и стека.
- Заголовок `X-Request-Id` возвращается всегда: свой, если клиент его прислал,
  сгенерированный — если нет.
- Идентификаторы запросов уникальны при конкурентной подаче.

### Тест утечек: что именно доказано

`internal/obs/leak_test.go` — внешний тест (`package obs_test`), поднимает
настоящий сервер на петле и читает журнал и метрики в том виде, в каком их
увидит оператор. Разметка — 23 синтетических значения, по одному на каждый тип
реестра `pii` (проверяется равенство `len(marked) == pii.Count-1`); значения
придуманы для теста и не берутся из справочников детекции. Детекция задана
тестовым сканером `markScanner`, как это уже сделано в `proxy_test.go`:
инвариант приватности обязан проверяться независимо от готовности сканеров.

Цикл: успешный прямой шаг, обратный шаг, битый JSON, запрос без `payload_id`,
тело сверх предела (413), затем снятие `/metrics`. Журнал пишется в буфер на
уровне **debug** — самом разговорчивом режиме. Поиск ведётся **по каждому
значению отдельно** в журнале, теле `/metrics` и телах всех ответов; сравнение
целого payload не применяется, потому что оно пропустило бы частичную утечку.
Ни одно значение не найдено.

Оговорки, важные при чтении результата:

- Тело **обратного шага** из поиска исключено намеренно: по REQ-103 оно и есть
  сохранённый оригинал. Вместо поиска утечки оно сверяется с исходным текстом
  побайтово — это и есть проверка восстановления.
- Короткие числовые значения (CVV — 3 цифры, ПИН — 4) ищутся с проверкой
  соседних байтов: подстрока из трёх цифр неизбежно встречается внутри чисел
  метрик, и такое совпадение — ложная тревога, а не утечка. Для остальных
  значений поиск подстрочный, без послаблений.
- Тест защищён от пустого прохода: проверяется, что маскирование
  действительно выполнено (в ответе есть плейсхолдер каждого типа), что журнал
  не пуст и содержит `request_id`, `payload_id` и перечень типов, что
  экспозиция содержит счётчики. Иначе «ничего не найдено» ничего бы не значило.
- Обратный контроль прогнан вручную: во временную версию теста добавлена
  запись `logger.Info("...", "payload", leakPayload, "cvv", ..., "pin", ...)`,
  после чего тест упал по **всем 23** значениям, включая CVV и ПИН. Временная
  правка снята, файл восстановлен.

Кардинальность меток (`TestMetricsLabelsCarryNoIdentifiers`): в экспозиции нет
ни `payload_id`, ни `request_id` — ни как имени метки, ни как значения;
разобраны все строки, имена меток сверены с закрытым перечнем
(`endpoint`, `op`, `outcome`, `type`, `le`), значения — с перечислениями.
В `metrics_test.go` перечислимость дополнительно закреплена на этапе
компиляции присваиванием сигнатур методов `Metrics`.

### Блокер: отказ по перегрузке не наблюдаем

**Дефект в `internal/httpapi/middleware.go` (файл вне `owns`, не изменялся).**
В `wrap` ветка отказа по пределу одновременной обработки выполняется **до**
присвоения `rid` и создания `log`, поэтому ответ `429` не оставляет следов:

1. заголовок `X-Request-Id` не возвращается — теряется даже тот, что прислал
   клиент (нарушает AC-8 «возвращается всегда»);
2. в теле ответа `request_id` пуст;
3. в журнал не пишется ничего (REQ-700 требует записи по каждому запросу);
4. счётчик `aigw_requests_total` с `outcome="overloaded"` не увеличивается,
   хотя значение метки заведено именно под этот случай (REQ-702 требует числа
   запросов по исходам).

Проверено фактическим прогоном: при заполненном семафоре ответ — `429`,
заголовки — только `Content-Type` и `Retry-After`, строк `aigw_requests_total`
с значениями нет, буфер журнала пуст.

Последствие: backpressure невидим и оператору, и в отчёте по нагрузочному
прогону. Отказы по пределу одновременной обработки — ровно тот показатель,
который нужен по критерию 6 и для объяснения просадок в нагрузочном прогоне.
Сейчас единственный видимый учёт `overloaded` — переполнение хранилища
в `process.go`, а не сам предел конкурентности.

Предложенная правка (внести оркестратору; менять только `wrap`):

```go
func (s *Server) wrap(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		started := time.Now()

		// Идентификатор присваивается до проверки предела: ответ об отказе
		// тоже обязан быть привязан к записи журнала.
		rid := r.Header.Get("X-Request-Id")
		if rid == "" {
			rid = "r" + strconv.FormatUint(requestSeq.Add(1), 36)
		}
		w.Header().Set("X-Request-Id", rid)
		log := s.deps.Logger.With("request_id", rid)

		select {
		case s.sem <- struct{}{}:
			defer func() { <-s.sem }()
		default:
			log.Warn("отказ по пределу одновременной обработки", "path", r.URL.Path)
			s.deps.Metrics.Request(endpointOf(r.URL.Path), obs.OpMask,
				obs.OutcomeOverloaded, time.Since(started).Seconds())
			w.Header().Set("Retry-After", strconv.Itoa(retryAfterSeconds))
			writeError(w, http.StatusTooManyRequests, "сервис перегружен, повторите запрос")
			return
		}

		defer func() {
			if rec := recover(); rec != nil {
				log.Error("паника при обработке запроса", "panic", rec, "path", r.URL.Path)
				writeError(w, http.StatusInternalServerError, "внутренняя ошибка обработки")
			}
		}()

		next.ServeHTTP(w, r.WithContext(withRequestID(r.Context(), rid)))
	})
}
```

`endpointOf` — маленький помощник в том же файле, отображающий маршрут в
`obs.Endpoint` (`/process` → `EndpointProcess`, `/v1/chat/completions` →
`EndpointChat`, остальное → `EndpointProcess`). Альтернатива — передавать
`obs.Endpoint` параметром в `wrap`, но это трогает `server.go`, `proxy.go` и
места вызова в чужих тестах, поэтому предложен вариант без правки сигнатуры.

Проверка под эту правку уже написана: `TestMiddlewareOverloadIsObservable`
в `internal/httpapi/middleware_test.go`. Сейчас она помечена `t.Skip` со
ссылкой на этот блокер, чтобы прогон оставался зелёным для соседних задач
волны. После внесения правки снять `t.Skip` — остальное тело теста менять
не нужно.

### Что закрыто и что нет

Закрыты AC-1 … AC-7 и AC-9. **AC-8 закрыт частично**: `X-Request-Id`
возвращается и на успешных ответах, и на ошибках обработчика (400, 413, 500),
уникален при конкурентной подаче (64 горутины, `-race`), свой идентификатор

есть блокер выше.

Осталось непроверенным:

- Экспозиция не проверялась настоящим Prometheus — формат разбирается
  собственным парсером текстового формата в тесте.
- Поведение под реальной нагрузкой (Latency, RPS, TPS по критерию 6) —
  предмет нагрузочного прогона, не этой задачи; здесь проверена только
  корректность съёма показателей.
- Полнота детекции в тесте утечек не участвует: разметка задана тестовым
  сканером. Отсутствие немаскированного значения в ответе успешного шага
  доказывает работу маскирования, а не качество сканеров.
