## Почему задача появилась

Навык технического жюри при первом же прогоне нашёл расхождение: README
описывал `POST /api/v1/mask` и `POST /api/v1/unmask`, а маршруты нигде не
регистрировались. Пути встречались только в сопоставлении меток метрик.

Документ поправлен немедленно — описывать несуществующее нельзя. Но сами
эндпоинты полезны и стоят реализации: потребителю может быть нужно
замаскировать текст без обращения к модели, а восстановить — отдельным
вызовом позже.

Это прямо работает на критерий внедряемости: чем проще подключить нового
потребителя, тем выше оценка.

## Что сделать

Два эндпоинта, оба требуют ключ потребителя, оба применяют его политику.

**`POST /api/v1/mask`**

```
{"text": "строка", "id": "необязательный идентификатор корреляции"}
  → {"masked": "строка", "id": "...", "types": ["full_name", ...], "counts": {...}}
```

Если идентификатор не передан — сервис выдаёт свой. Соответствие сохраняется
в области потребителя, как и для контракта автопроверки.

**`POST /api/v1/unmask`**

```
{"masked": "строка", "id": "идентификатор"}
  → {"text": "строка"}
```

Восстановление разрешено только потребителю с правом `demask` и только для
соответствий его собственной области. Чужой идентификатор ничего не
раскрывает — это REQ-404, и он проверяется тестом.

## Требования

- Ответы не содержат значений ПД сверх того, что запрошено: `types` и счётчики
  по типам, но не сами значения.
- Предел обработки запроса применяется так же, как на `/process`.
- Инвариант fail-closed: если защиту завершить не удалось, маска не выдаётся.
- Метки метрик уже заведены — `obs.EndpointMask` и `obs.EndpointUnmask`.
