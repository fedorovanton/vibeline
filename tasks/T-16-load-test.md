## Цель

Измерить латентность и пропускную способность в том же режиме, в котором
работает проверяющая система, и выдать цифры для критерия 5.

## Профиль нагрузки

Закрытый контур: фиксированное число соединений, каждое отправляет следующий
запрос **только после** получения ответа на предыдущий. Это не открытый
контур с заданным RPS — воспроизводить надо именно закрытый.

Отсюда следует: пропускная способность равна `соединения / средняя латентность`.
При 200 соединениях 1000 RPS достижимо ровно тогда, когда средняя латентность
не превышает 200 мс. Это соотношение надо явно напечатать в отчёте: оно
объясняет, почему цифра RPS не может быть выше, чем позволяет латентность.

## Что сделать

Отдельный Go-модуль в `tools/loadtest/` со своим `go.mod`.

Прогон: разгон до заданного числа соединений, затем удержание. По каждому
элементу — пара запросов с одним `payload_id`: маскирование, затем
демаскирование. Идентификаторы уникальны, элементы корпуса переиспользуются.

Измеряется: успешный goodput, среднее, p50, p95, p99, максимум; отдельно по
маскированию, по демаскированию и суммарно. Считаются коды ответов, включая
429 — они не являются ошибкой, но сохраняются для статистики.

Отдельно снимается: RSS процесса, размер кучи, число сборок мусора и время в
них — через `GET /metrics` и `runtime/metrics` целевого процесса, если он
локальный.

Отдельные режимы прогона по флагу:

- смешанный: короткие и длинные тексты;
- только длинные: тексты на 100 000 токенов, проверка на устойчивость;
- поиск предела: увеличение числа соединений до момента, когда латентность
  перестаёт укладываться в 1 секунду.

Флаги: `-url`, `-corpus`, `-conns` (по умолчанию 200), `-duration`
(по умолчанию 5m), `-mode`, `-json`, `-timeout` (10 с).

Отчёт обязан фиксировать условия измерения: версия Go, число ядер, объём
памяти, число соединений, длительность, состав нагрузки. Без них цифры
несравнимы. Числа до измерения помечаются TARGET, полученные — RESULT.

### Что сделано

Модуль `tools/loadtest/` (`module loadtest`, Go 1.26, только стандартная
библиотека, `ai-gateway` не импортируется — проверено `grep`, упоминания есть
только в комментариях):

| Файл | Ответственность |
|---|---|
| `main.go` | флаги, оркестрация прогона, режим `limit`, сборка отчёта |
| `runner.go` | закрытый контур: воркеры, пара запросов на элемент, обработка 429 |
| `corpus.go` | чтение корпуса T-14 (JSONL) и встроенный набор на случай его отсутствия |
| `hist.go` | гистограмма латентности (схема HdrHistogram), перцентили |
| `target.go` | снятие `GET /metrics`, RSS через `ps`, разбор журнала `gctrace` |
| `report.go` | текстовый и JSON-отчёт, условия измерения, предел закрытого контура |

Закрытый контур обеспечен на уровне транспорта: у каждого воркера свой
`http.Client` с `MaxConnsPerHost: 1`, поэтому второй запрос физически не уйдёт
до ответа на первый. Корпус T-14 не обязателен: при отсутствии файла берётся
встроенный синтетический набор, а в режиме `long` достраиваются тексты на
100 000 токенов.

### Условия измерения

Go 1.26.0, darwin/arm64, 10 ядер, 32 ГиБ памяти. Клиент и сервис — на одной
машине через loopback, то есть делят ядра: наблюдаемая клиентом латентность
завышена, и собственная гистограмма сервиса приведена рядом как более чистая
величина. Сервис собран из `cmd/ai-gateway`, запущен с `GODEBUG=gctrace=1`.

Порт: штатный `:8080` на этой машине занят посторонним процессом
(`obscura-gateway`), из-за чего запросы уходили не в наш сервис. Прогоны
выполнены на `127.0.0.1:8090` через копию `config.yaml` во временном каталоге;
`config.yaml` в репозитории не изменялся.

### Наблюдение для оркестратора: расхождения восстановления при вытеснении

В прогонах режима `limit` появились 24–32 случая, когда обратный шаг вернул не
исходный текст. Они возникли только там, где хранилище вытесняло соответствия по
лимиту `store.max_bytes: 2GiB` (258 556–310 145 вытеснений за прогон).

Контрольный прогон: 3 200 соединений, 20 с, корпус только из коротких текстов —
хранилище в лимит не упирается (0 вытеснений), расхождений **0** на 283 428 пар.
То есть расхождение связано с вытеснением соответствия между прямым и обратным
шагом, а не с конкурентностью. По REQ-101 вытесненное соответствие превращает
обратный шаг в новый вход, и текст закономерно не совпадает. Решение — за
владельцем `internal/store` и конфигурации, инструмент фиксирует факт и печатает
рядом счётчик вытеснений.

### Что осталось незакрытым

- **Куча и сборки мусора снимаются только через `GODEBUG=gctrace=1`.** Сервис не
  публикует счётчиков Go-рантайма на `/metrics` и не включает `pprof`, а
  `runtime/metrics` чужого процесса извне не читается. Без флага `-gctrace`
  раздел помечается `NOT_MEASURED`, а не заполняется догадкой. Если нужен штатный
  путь — добавить Go-коллектор в `internal/obs`, это вне `owns` T-16.
- **Аллокации — оценка, а не счётчик.** Считаются по приростам кучи между
  сборками из `gctrace`; точного `mallocs_total` снаружи процесса нет.
- **Измерение на совмещённом стенде.** Клиент и сервис делят 10 ядер, поэтому
  клиентские цифры — верхняя оценка. Прогон против публичного URL из AGENTS §2
  не выполнялся.
- **Корпус T-14 не использовался**: на момент прогона файла не было, работал
  встроенный набор. Повторить с реальным корпусом стоит после закрытия T-14.
