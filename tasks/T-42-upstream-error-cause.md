## Цель

Отказ обращения к модели записывается как `chain_status: upstream_error` без
кода ответа и текста ошибки. По такой записи причину установить нельзя.

## Как это выяснилось

22.09.2026 сервис в контейнере не получал ответа модели. В журнале было
только `upstream_error` и `llm_ms: 820`. Ненулевое время сбивало со следа:
оно означало, что запрос уходит и ответ приходит, то есть дело не в ключе.
Причину — отсутствие в образе корней, которыми подписан AlfaGen, —
пришлось искать сверкой вызова с хоста и из контейнера вручную.

На защите такой отладки не будет.

## Что сделать

Записывать причину отказа: код ответа HTTP при ответе сервера, класс ошибки
при сетевом отказе (таймаут, отказ TLS, отказ разрешения имени). Тело ответа
модели в журнал не писать — в нём может оказаться эхо запроса.

Показать причину и на стенде: сейчас там «модель не ответила», чего для
разбора недостаточно.

## Критерии приёмки

- [x] AC-1 отказ с кодом HTTP пишет код в журнал
- [x] AC-2 отказ TLS, таймаут и отказ разрешения имени различимы в журнале
- [x] AC-3 тест подтверждает, что тело ответа модели в журнал не попадает
- [x] AC-4 инвариант приватности не нарушен: прогон leak_test остаётся зелёным

## Команда проверки

go test -count=1 ./internal/llm ./internal/gateway ./internal/obs

## Журнал

### Что сделано

`internal/llm/client.go` — причина отказа стала данными, а не текстом:

- тип `Failure{Class, Status, Reason, Err}` и закрытый перечень классов
  `FailureClass`: `http_status`, `timeout`, `tls`, `dns`, `connect`, `network`,
  `canceled`, `bad_response`, `bad_request`, `unknown`. Перечень закрытый —
  значение годится и в журнал, и в метку метрики;
- `Classify(err) Failure` — одна точка разбора для вызывающего кода. Ошибка
  чужой реализации `Chatter` получает класс `unknown`, поэтому поле причины
  заполнено при любом источнике отказа;
- все возвраты ошибок `Chat`/`do` переведены на `*Failure`. Код ответа больше
  не форматируется в строку, а лежит в поле `Status`;
- тело ответа модели по-прежнему не читается в сообщение. Ошибка `json` не
  оборачивается сознательно: её текст цитирует разбираемые байты, то есть тело
  ответа модели.

`internal/gateway/proxy.go` — причина доведена до слоя, который пишет журнал:

- в `ProxyResult` добавлены `UpstreamClass`, `UpstreamStatus`, `UpstreamReason`;
- заполняются в единственной точке выпуска наружу, сразу после `model.Chat`;
- метод `UpstreamNote()` собирает готовую строку причины для журнала и стенда.

Поведение повторов, таймаутов и коды ответа наружу не менялись: правка
касается только наблюдаемости отказа.

собирает настоящую запись журнала через `slog.JSONHandler` из тех же полей,

запроса в теле, и ищет каждое размеченное значение по отдельности. Тест сначала
убеждается, что причина в записи есть: запись без причины утечки тоже не
содержит.

### Живой прогон на своём экземпляре (:8092)

Собран бинарник, конфигурация скопирована в `/tmp/config-t42.yaml`, адрес
модели подменялся с перезагрузкой по SIGHUP. Контейнер на :8080 не трогался.
Отказы воспроизведены фальшивой моделью на петле (401, самоподписанный
сертификат, молчание) и подменой адреса (несуществующее имя, закрытый порт).
Записи журнала на `POST /v1/chat/completions`:

### Требуется от оркестратора: показ причины на стенде

Файлы не мои, правки не вносил. Причина лежит в `gateway.ProxyResult` и берётся
одной строкой.

1. `internal/httpapi/ui.go`, `fillChain` (ветка `errors.Is(perr, gateway.ErrUpstream)`,
   около строки 788) — дополнить примечание цепочки:

   ```go
   res.ChainStatus = "upstream_error"
   res.ChainNote = "модель не ответила; защита запроса при этом выполнена полностью"
   if note := out.UpstreamNote(); note != "" {
       res.ChainNote += ". Причина: " + note
   }
   ```

2. `internal/httpapi/ui.go`, строка журнала стенда `log.Info("стенд: прогон выполнен", ...)`
   (около строки 335) — добавить поля `"upstream_class", out.UpstreamClass` и
   `"upstream_status", out.UpstreamStatus`. Сейчас эта запись состоит из
   `chain_status` и `llm_ms` — ровно та, по которой 22.09.2026 причину
   установить не удалось.

3. `internal/httpapi/proxy.go`, `log.Warn("модель не ответила", ...)` (строка 155) —
   поля `upstream_class` и `upstream_status` желательны как машиночитаемые.
   Код и класс там уже видны в поле `error`, так что правка не блокирующая.

4. `web/index.html` править **не нужно**: стенд уже показывает `chain_note`
   (строки 1165 и 1343), и причина появится в нём сама после пункта 1.

Проверено, что без этих правок стенд по-прежнему отвечает
`chain_note: "модель не ответила; защита запроса при этом выполнена полностью"`.

### Что осталось непроверенным

- Класс `dns` живым резолвером проверен (`*.invalid`), классы `network` и
  `canceled` живым прогоном не воспроизводились — только тестами.
- Отказ TLS проверен на самоподписанном сертификате, а не на пустом хранилище
  корней в образе: сборка контейнера в задачу не входит и в `owns` её нет.
- Метка класса отказа в метриках не заводилась: `internal/obs/metrics.go` не
  мой файл. Если нужен счётчик отказов по классам — это отдельная задача.
- Побочное наблюдение, к задаче отношения не имеет: живой AlfaGen ответил
  HTTP 200 на запрос с заведомо неверным ключом доступа. Воспроизведено один
  раз на своём экземпляре; `.env` не менялся. Проверять на 401 пришлось
  фальшивой моделью. Возможно, стоит завести отдельную задачу.
