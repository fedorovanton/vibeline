## Цель

`scripts/demo.sh` ходит с фиксированными `payload_id`: `demo-full`,
`demo-case`, `demo-traps`, `demo-namesake`. Пока соответствие по такому
идентификатору живёт в хранилище (TTL 30 минут), прогон с изменённым текстом
сценария печатает ложное «✗ РАСХОЖДЕНИЕ С ОРИГИНАЛОМ».

Бизнес-жюри назвало это в отчёте: «на живой защите повторный запуск выглядел
бы как сбой» (`.agents/runtime/jury-exec-review/REPORT.md`, критерии 2 и 4).

## Механика

Направление в `internal/gateway/process.go` определяется сопоставлением
payload с сохранённой записью, а не счётчиком вызовов. Ветка `default:`
срабатывает, когда вход не равен ни сохранённому оригиналу, ни сохранённой
маске: вход маскируется как новый, **запись не обновляется**, и второй вызов
сценария получает «маску маски».

Формулировка жюри при этом неточна, и это важно: **чистый повтор
немодифицированного скрипта против того же процесса сходится**, что закреплено
тестами `TestProcessForwardRetryIsIdempotent` и `TestProcessIdentityMaskRoundTrip`.
Ломает демонстрацию любое из:

1. текст сценария поправили, а запись по старому идентификатору жива;
2. тот же `demo-*` дёрнули вручную с другим текстом;
3. запись исчезла между двумя вызовами одного сценария: перезапуск сервиса,
   истечение TTL, вытеснение по `store.max_entries` или `store.max_bytes`.

### Последствие хуже, чем ложная сверка

Воспроизведено на живом сервисе. Два **разных** текста дали посимвольно
одинаковую маску `Клиент [ФИО_1], паспорт [ПАСПОРТ_1]`. Поэтому обратный шаг
совпал со `stored.Masked` **первой** записи и вернул **чужой оригинал** —
«Иванов Иван Иванович» вместо «Петров Пётр Петрович».

На демонстрации это выглядит не как расхождение сверки, а как подмена данных
клиента. Само поведение сервиса корректно и защищает обратный шаг от затирания
неизвестным входом; дефект — в скрипте, который переиспользует идентификаторы.

### Второе следствие: показ «пустеет»

На ветках `OpMaskRetry` и `OpUnmask` поле `Mask` пусто, поэтому
`aigw_pii_masked_total` не растёт, а в журнал уходит `masked_types: []`.
Финальный блок «── Метрики» выглядит мёртвым даже там, где сверка сошлась.
Вероятно, именно это жюри и приняло за сбой.

## Что сделано

`RUN_ID` в шапке скрипта, суффикс к идентификатору каждого сценария. Значение
переопределяется извне: `RUN_ID=<значение>` повторяет прогон с теми же
идентификаторами — путь проверки повтора прямого шага сохранён.

## Критерии приёмки

- [x] AC-1 Два запуска подряд против одного процесса без перезапуска дают
      «✓ совпадает с оригиналом побайтово» во всех сценариях.
- [x] AC-2 Второй запуск наращивает `aigw_pii_masked_total`, а не оставляет
      счётчик на месте.
- [x] AC-3 Прогон с изменённым текстом сценария не печатает ложное
      расхождение.
- [x] AC-4 `RUN_ID=<значение> bash scripts/demo.sh` повторяет прогон с
      заданным идентификатором.
- [x] AC-5 Скрипт остаётся совместим с `bash scripts/demo.sh <адрес>` и с
      переменной `HOST`.

## Команда проверки

```bash
make run-bg PORT=8105
bash scripts/demo.sh http://127.0.0.1:8105 && bash scripts/demo.sh http://127.0.0.1:8105
make stop
```
