# 03. Требования

> Нормативный источник: `docs/init/3 Техническое задание трека.pdf`, дополнительно
> сверено с `docs/init/4 brief-task.md` и визуальными материалами задания.

Сервис должен выявлять и обеспечивать защиту персональных данных в соответствии с
действующим законодательством Российской Федерации, применимой нормативной базой и
требованиями ЦБ.

## 3.1. Ключевые требования

- Решение должно легко встраиваться в цепочку взаимодействия
  «система-потребитель — LLM».
- Обязательное покрытие описанных типов персональных данных.
- Строгое соблюдение требований безопасности и приватности: никаких утечек,
  шифрование, минимизация данных.
- Недопустимость критичных ошибок и соблюдение уровня качества обработки.
- Выполнение SLA на ответы и действия (скорость, доступность, стабильность).

## 3.2. Функциональные требования

### 3.2.1. Идентификация типов персональных данных

Необходимо однозначно идентифицировать следующие типы ПД:

| Категория | Типы ПД |
|-----------|---------|
| Личные данные | ФИО, Дата рождения, Место рождения, Гражданство |
| Паспорт РФ | Серия и номер паспорта, Орган, выдавший паспорт, Код подразделения, Дата выдачи паспорта |
| Водительское удостоверение | Серия и номер водительского удостоверения |
| Адрес | Адрес (в т.ч. отдельно: страна, индекс, город, улица, дом, квартира и т.п.) |
| Контакты | Email, Номер телефона |
| Финансовые | ИНН, Номер платёжной банковской карты, CVV-код, Пин-код карты, Имя держателя карты |

Итого перечислено **17 типов/категорий данных**. Адрес считается одним типом с
обязательной поддержкой отдельных компонентов: страна, индекс, город, улица, дом,
квартира и т. п.

**Требования к идентификации:**

- Проработать механизм определения **принадлежности данных именно к персональным**:
  например, упоминание поэта Александра Пушкина не является персональными данными,
  как и адрес отделения Банка.
- Возможность **расширения списка** идентифицируемых персональных данных.
- Идентификация **не должна зависеть от регистра**.
- **Логирование** выявленных типов персональных данных в тесте по каждому запросу.

### 3.2.2. Маскирование

Необходимо учесть разные вариации написания персональных данных, например:

- регистр;
- разное расположение года, месяца и даты (например, `мм.дд.гггг`, `гггг.дд.мм`);
- написание даты текстом, а не числами;
- разделяющие слова — «серия хххх номер хххххх» и т.п.

### 3.2.3. Демаскирование

Преобразование замаскированного текста в незамаскированный **с сохранением
местоположения знаков**.

### 3.2.4. Общие требования

- Подробное логирование на каждом этапе работы сервиса.
- Метрики для контроля **Latency, RPS, TPS** (tokens per second).
- Наличие **ограниченного списка систем**, которые имеют возможность обращаться в сервис.
- **Гибкая настройка:**
  - списка систем (вкл/откл возможности обращения в модуль);
  - перечня типов персональных данных для идентификации и маскирования в зависимости
    от системы;
  - наличия демаскирования в зависимости от системы;
  - краткая инструкция по настройке (не более 5 предложений).
- **Высокое качество** идентификации/маскирования/демаскирования — **95%**.
- Обработка крупных массивов текста — **до 100 000 токенов**.

Требование 95% задано ТЗ как целевой уровень качества обработки; конкретная методика
подсчёта для общего сервиса в ТЗ не раскрыта. Для автоматической проверки отдельно
указана span-based нормированная метрика Левенштейна для результата маскирования.

> ⚠️ **Уточнено организаторами.** Эталонной маски не существует — метрика оценивает
> качество сокрытия относительно оригинала. Способ и длина замены свободные, полное
> сокрытие значения предпочтительнее частичного, избыточное маскирование (служебные
> слова, вся строка без необходимости) штрафуется, а пропуски штрафуются сильнее
> лишних масок. См. [07-clarifications.md §7.1](07-clarifications.md).

## 3.3. Нефункциональные требования

- **Безопасность:** все данные обрабатываются в защищённом контуре, соответствие
  внутренним стандартам ИБ банка.
- **Надёжность:** корректная обработка ошибок API, деградация функционала при
  недоступности сервисов, понятные сообщения пользователю.
- **Производительность:** Latency — не более 1 секунды, RPS — 1000.
- **Масштабируемость:** архитектура допускает добавление настроек для новых типов ПД
  и увеличение RPS при сохранении Latency.

## 3.4. Дополнительные плюсы (бонусные возможности)

- Дополнительная реализация **токенизации/детокенизации** либо замены
  **синтетическими данными**.
- Гибкая настройка **вида маскирования/токенизации** в зависимости от системы.
- Возможность держать **RPS 2000** при Latency не более 1 секунды.
- Идентификация документов, удостоверяющих личность, **кроме паспорта РФ**.
- Маскирование только при наличии **нескольких однозначно идентифицированных типов ПД**
  (например, «пин-код карты» — не маскируем; «пин-код карты + номер карты» —
  маскируем). Возможность изменения этих настроек.
