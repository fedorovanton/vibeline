# 04. Контракт API и нагрузочное тестирование

> Нормативный источник: приложение A и приложение B в `docs/init/3 Техническое
> задание трека.pdf`. Контракт является обязательным минимумом будущего сервиса.

## 4.1. Автоматическая проверка решений

Обе проверки **обязательны**. Решение, не прошедшее автоматическую проверку качества
кода, а также не развёрнутое для нагрузочного тестирования, **не будет учтено**.

> ⚠️ **Уточнено организаторами.** Отсекающим барьером остаётся только развёртывание:
> без доступного URL с `POST /process` решение не оценивается. Проверка качества кода
> засчитывается в любом случае, но её результаты могут снизить баллы по связанным
> критериям. См. [07-clarifications.md §7.5](07-clarifications.md).

### 4.1.1. Проверка качества кода

Как только решение загружается в формате **zip-файла (и только zip!)**, автоматически
запускается проверка качества кода. Без её прохождения решение не будет учтено.

> ⚠️ **Уточнено организаторами.** Проверка считается успешной в любом случае и
> отсекающим барьером не является, однако её результаты могут снизить баллы жюри по
> связанным критериям. См. [07-clarifications.md §7.5](07-clarifications.md).

**Как правильно упаковать решение в zip:**

- Упаковывайте только исходный код решения.
- Не добавляйте объёмные файлы — датасеты, дампы, архивы, медиа, скомпилированные
  бинарники.
- Не упаковывайте build-директории и зависимости:
  - `node_modules`, `.venv`, `venv`, `env` — каталоги зависимостей;
  - `target`, `build`, `dist`, `out`, `bin`, `obj` — каталоги сборки;
  - `.git`, `.idea`, `__pycache__`, `coverage` — служебные каталоги.
- Один архив в формате `.zip` разумного размера, с исходным кодом в корне или в
  понятной структуре.

> Совет: чем чище и легче архив, тем быстрее и надёжнее проходит проверка.

### 4.1.2. Нагрузочное тестирование

Потребуется развернуть решение, реализующее контракт API (эндпоинт `POST /process`).
Проверяющая система подаёт нагрузку по эталонному датасету и оценивает точность
маскирования и демаскирования, а также поведение под нагрузкой.

## 4.2. Контракт API «/process»

Единый контракт, который команды-участники должны реализовать на своём сервисе.
Проверяющая система обращается к этому эндпоинту для нагрузочного тестирования.

### Схема запроса/ответа

```
POST /process
Content-Type: application/json

{ "payload": "<строка>", "payload_id": "<идентификатор>" }
  → 200
{ "result": "<строка>" }
```

### Логика (одинакова для всех)

- Эндпоинт **один** — обрабатывает и маскирование, и демаскирование.
- Направление определяется по `payload_id` — используйте его как **ключ корреляции**
  «маскирование → демаскирование».
- **Первый запрос** с новым `payload_id` — маскирование (`payload` = исходная строка)
  → верните маску и запомните соответствие.
- **Второй запрос** с тем же `payload_id` — демаскирование (`payload` = ваша маска)
  → верните исходную строку.
- Ответ всегда: `{"result": "…"}`.

Практическое следствие: состояние соответствия должно быть доступно между двумя
запросами одной пары и не должно теряться из-за ретрая или параллельной обработки.
ТЗ требует идемпотентность по `payload_id`, но не предписывает конкретное хранилище,
срок жизни записей или стратегию очистки — это решение реализации.

### OpenAPI-спецификация (process_api.yaml)

```yaml
openapi: 3.0.3
info:
  title: Модуль безопасности ПД — контракт /process
  version: "1.0.0"
  description: |
    Единый контракт, который команды-участники ДОЛЖНЫ реализовать на своём сервисе.
    Система проверки AlfaSonar обращается к этому эндпоинту для нагрузочного тестирования
    и оценки точности маскирования/демаскирования персональных данных.

    ВАЖНО (логика проверки одинакова для всех команд):
      * Эндпоинт один — `POST /process`. Он обрабатывает и маскирование, и демаскирование.
      * Проверка идёт парами по каждому элементу датасета и коррелируется полем `payload_id`:
          1) ПРЯМАЯ проверка (маскирование): приходит первый запрос с новым `payload_id`,
             `payload` = исходная строка. Сервис ДОЛЖЕН вернуть замаскированную строку и
             запомнить соответствие по `payload_id`.
          2) ОБРАТНАЯ проверка (демаскирование): приходит второй запрос с ТЕМ ЖЕ `payload_id`,
             `payload` = ранее возвращённая вами замаскированная строка. Сервис ДОЛЖЕН вернуть
             исходную (демаскированную) строку.
      * `payload_id` уникален для каждого элемента в рамках прогона — используйте его как ключ
        корреляции «маскирование → демаскирование».
      * Ответ всегда: `{"result": "<строка>"}`.

servers:
  - url: https://your-solution.example.com
    description: HTTPS (self-signed допускается — проверка идёт с ssl_verify=false)
  - url: http://your-solution.example.com
    description: HTTP также поддерживается

paths:
  /process:
    post:
      operationId: process
      summary: Маскирование/демаскирование строки (коррелируется по payload_id)
      requestBody:
        required: true
        content:
          application/json:
            schema:
              $ref: "#/components/schemas/ProcessRequest"
      responses:
        "200":
          description: Успешная обработка
          content:
            application/json:
              schema:
                $ref: "#/components/schemas/ProcessResponse"
        "429":
          description: |
            Слишком много запросов. Допустимо под нагрузкой. Проверяющая система применит
            ожидание и ретраи; если 429 не проходит — это значимый результат (решение не держит нагрузку).
        "4XX":
          description: Ошибка запроса
        "5XX":
          description: Внутренняя ошибка сервиса

components:
  schemas:
    ProcessRequest:
      type: object
      required: [payload, payload_id]
      properties:
        payload:
          type: string
          description: |
            Строка для обработки. На прямом шаге — исходный текст с ПД; на обратном шаге —
            ваша же ранее возвращённая замаскированная строка (тот же payload_id).
          example: "Клиент Иванов Иван Иванович, паспорт 4509 123456"
        payload_id:
          type: string
          description: Идентификатор корреляции. Один и тот же для пары маскирование→демаскирование.
          example: "8a77d363c7c044b49b41d7b8a448243a"
    ProcessResponse:
      type: object
      required: [result]
      properties:
        result:
          type: string
          description: Результат обработки (замаскированная строка на прямом шаге, исходная — на обратном).
          example: "Клиент И. И. И., паспорт 45** ****56"
```

## 4.3. Инструкция по нагрузочному тестированию

### Что нужно реализовать

- Один HTTP-эндпоинт `POST /process` по контракту из Приложения A.
- Сервис можно развернуть на **http или https** (в т.ч. с самоподписанным
  сертификатом) — проверка идёт с `ssl_verify=false`, ошибок сертификата не будет.

### Логика проверки (пошагово)

Проверка идёт по каждому элементу датасета **парой запросов с одним `payload_id`**:

1. **Прямая проверка (маскирование).** Система шлёт исходную строку с новым
   `payload_id` → сервис возвращает маску и запоминает соответствие. Результат
   оценивается span-based метрикой на базе нормированного расстояния Левенштейна
   `[0..1]`.

   > ⚠️ **Опровергнуто ответами организаторов.** Эталонной маски не существует:
   > метрика сравнивает качество сокрытия **относительно оригинала**, а не близость
   > к образцовой маске. Формат и длина замены свободные. Подробности и следствия —
   > [07-clarifications.md §7.1](07-clarifications.md).
2. **Обратная проверка (демаскирование).** Система шлёт вашу же маску с тем же
   `payload_id` → сервис возвращает исходную строку. Результат сравнивается с исходной
   строкой из датасета.

**Проверяемые категории ПД:** ФИО, даты, паспорт, гражданство, орган выдачи, код
подразделения, в/у, адрес, email, телефон, ИНН, номер карты, CVV, ПИН, имя держателя
и сложные предложения.

### Требования к надёжности (обязательно учесть)

- **Таймаут** одного запроса — **10 секунд**. Ответ дольше считается неответом.
- **Ретраи** — до 2 на каждый запрос (итого до 3 попыток). Делайте эндпоинт
  **идемпотентным** по `payload_id`.
- **429 (Too Many Requests)** допустим под нагрузкой: система применит ожидание и
  ретраи (учитывается `Retry-After`). Если 429 сохраняется — это значимый результат
  (решение не держит нагрузку) и попадёт в метрики.
  - Если 429 не проходит на маскировании — демаскирование по этому элементу не
    запрашивается; если на демаскировании — учитывается, и проверка продолжается.
- **Стоп при недоступности:** после **5 невалидных запросов подряд** прогон
  останавливается (429 невалидным не считается и счётчик не сбрасывает; успешный
  ответ сбрасывает счётчик).
- **Нагрузка:** по умолчанию прогон идёт по всем категориям **~5 минут** с целевым
  **RPS 1000**; элементы датасета переиспользуются. Целевое значение latency — **не
  более 1 c** (ориентир, не жёсткий лимит).

> ℹ️ **Уточнённый профиль нагрузки.** Подача идёт с разгоном, средний RPS около 330 с
> пиками до 1000, параллельность — до 200 одновременных коннектов, каждый из которых
> ждёт ответа перед следующим запросом (закрытый контур). Измеряется только время
> ответа нашего сервиса. Пропускная способность равна `200 / средняя латентность`.
> См. [07-clarifications.md §7.2](07-clarifications.md).

`429` допускается только как управляемая реакция на перегрузку: проверяющая система
учитывает его и выполняет ожидание/ретраи по `Retry-After`. Устойчивые `4XX`/`5XX`,
таймауты и невалидные ответы влияют на доступность прогона и могут остановить его.

### Чек-лист «как пройти успешно»

- Реализован `POST /process` строго по контракту (`{payload, payload_id}` → `{result}`).
- Маскирование сохраняет соответствие по `payload_id`; повторный запрос с тем же id
  возвращает исходную строку.
- Ответ отдаётся быстро и стабильно под нагрузкой (RPS 1000+).
- Эндпоинт идемпотентен (безопасен к ретраям), корректно возвращает 429 при перегрузке.
- Сервис доступен по указанному URL (http или https) на момент прогона.

### Самопроверка формата контракта

Эталонная реализация формата контракта доступна для самопроверки — она демонстрирует
только формат обмена (правила маскирования берутся из ТЗ и одинаковы для всех):

```bash
curl -X POST https://process-test.holydev.space/process \
  -H "Content-Type: application/json" \
  -d '{"payload":"тестовая строка","payload_id":"selfcheck-1"}'
```

Самопроверка подтверждает только формат HTTP-обмена; она не подтверждает качество
правил идентификации, маскирования или демаскирования.
