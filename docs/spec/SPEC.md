# Спецификация поведения ai-gateway

Нормативное описание: что система обязана делать. Основания выбора — в
[DECISIONS.md](DECISIONS.md), устройство — в [ARCHITECTURE.md](ARCHITECTURE.md).

Слова «ДОЛЖЕН», «НЕ ДОЛЖЕН», «МОЖЕТ» употребляются строго. Каждое требование
имеет устойчивый идентификатор `REQ-…` и критерий приёмки.

## 1. Словарь

| Понятие | Определение |
|---|---|
| Потребитель | Система, обращающаяся к сервису. Определяется записью в конфигурации; область изоляции данных |
| Исходный текст | Строка, полученная от потребителя, до любых преобразований |
| Кандидат | Фрагмент исходного текста, похожий на значение некоторого типа ПД, с уровнем уверенности |
| Спан | Отобранный кандидат: диапазон байтов, тип и уровень уверенности. Спаны результата не пересекаются |
| Вето | Запрет на отнесение диапазона к персональным данным, выставленный контр-правилом |
| Маска | Текст, полученный заменой отобранных спанов |
| Плейсхолдер | Строка замены одного спана |
| Соответствие | Запись «идентификатор → исходный текст и маска», действующая в области одного потребителя |
| Область корреляции | Пара «потребитель, идентификатор». Единица изоляции соответствий |

## 2. Контракт автопроверки

### REQ-100. Эндпоинт

Сервис ДОЛЖЕН принимать `POST /process` с телом
`{"payload": строка, "payload_id": строка}` и отвечать `200` с телом
`{"result": строка}`.

Сервис НЕ ДОЛЖЕН требовать аутентификацию на этом эндпоинте: проверяющая
система шлёт запросы без заголовков.

Сервис НЕ ДОЛЖЕН отклонять запрос из-за неизвестных дополнительных полей:
контракт их не запрещает.

*Приёмка:* `TestProcessContract`, `TestProcessAcceptsUnknownFields`.

### REQ-101. Определение направления

Направление обработки ДОЛЖНО определяться сопоставлением `payload` с
сохранённым состоянием области корреляции. Счётчик вызовов использовать
НЕ ДОЛЖЕН: проверяющая система повторяет запрос при ошибке и при `429`.

Таблица переходов:

| Состояние области | `payload` | Действие | Ответ | Изменение состояния |
|---|---|---|---|---|
| соответствия нет | любой | детекция, политика, маскирование | маска | создаётся соответствие |
| есть | равен сохранённой маске, демаскирование разрешено | нет | сохранённый исходный текст | нет |
| есть | равен сохранённой маске, демаскирование запрещено | нет | сохранённая маска | нет |
| есть | равен сохранённому исходному тексту | нет | сохранённая маска | нет |
| есть | не совпал ни с чем, похож на маску (плейсхолдер, токен, `[ЗАЩИЩЕНО]`) | маскирование как нового входа | новая маска | **нет** |
| есть | не совпал ни с чем, на маску не похож | маскирование как нового входа | новая маска | соответствие **заменяется** |

Две последние строки нормативны. Вход, похожий на маску, — искажённый или
подделанный обратный шаг: соответствие, по которому ещё может прийти
настоящий обратный шаг, он перезаписывать НЕ ДОЛЖЕН. Обычный новый текст с
тем же `payload_id` — новая пара (повтор набора в пределах TTL): соответствие
заменяется, иначе обратный шаг второй пары получил бы маску или исходник
первой пары (DECISIONS.md I-22).

*Приёмка:* `TestProcessMaskThenUnmask`, `TestProcessForwardRetryIsIdempotent`,
`TestProcessNewTextSameIDStartsNewPair`, `TestInvariantProcessForgedPlaceholders`,
`TestProcessDemaskDeniedReturnsMask`.

### REQ-102. Идемпотентность

Повтор прямого шага с тем же идентификатором и тем же текстом ДОЛЖЕН
возвращать побайтово ту же маску.

Маскирование ДОЛЖНО быть чистой функцией от исходного текста и политики
потребителя: два вызова с одним входом обязаны дать одинаковый результат
независимо от порядка, времени и состояния хранилища.

*Приёмка:* `TestProcessForwardRetryIsIdempotent`, `TestProcessMaskIsPureFunction`.

### REQ-103. Точность восстановления

Обратный шаг ДОЛЖЕН возвращать исходный текст побайтово, включая пунктуацию,
пробелы и исходное написание.

Частный случай: если персональные данные не найдены и маска равна исходному
тексту, обратный шаг ДОЛЖЕН вернуть тот же текст, а не ошибку.

*Приёмка:* `TestProcessIdentityMaskRoundTrip`, тесты инвариантов T-19.

### REQ-104. Отказ обработки на `/process`

Если штатная обработка завершиться не может, сервис ДОЛЖЕН вернуть `200` с
маской, полностью скрывающей исходный текст, и сохранить соответствие.
Возвращать ошибку в этом случае НЕ ДОЛЖЕН.

Основание: пять невалидных ответов подряд останавливают весь нагрузочный
прогон. Ни одного исходного символа наружу при этом не уходит.

Исключение: если соответствие сохранить не удалось, сервис ДОЛЖЕН вернуть
`429` с заголовком `Retry-After`. Возвращать маску без сохранённого
соответствия НЕ ДОЛЖЕН: молчаливая потеря восстановления хуже явного отказа
по одному элементу.

*Приёмка:* `TestMaskFullTextHidesEverything`, тесты отказа хранилища T-19.

### REQ-105. Коды ответа

| Условие | Код | Дополнительно |
|---|---|---|
| успех | `200` | тело `{"result": …}` |
| тело не является корректным JSON | `400` | |
| отсутствует `payload_id` | `400` | |
| тело превышает предел | `413` | |
| предел одновременной обработки исчерпан | `429` | `Retry-After` обязателен |
| хранилище переполнено | `429` | `Retry-After` обязателен |
| обработка не уложилась в `server.request_timeout` (REQ-604) | `429` | `Retry-After` обязателен |
| непредвиденный отказ | `500` | тело без персональных данных |

Тела ответов об ошибках НЕ ДОЛЖНЫ содержать исходный текст и значения ПД.

*Приёмка:* `TestProcessRejectsMissingPayloadID`, `TestProcessRejectsBrokenJSON`,
`TestProcessRejectsOversizedBody`, `TestErrorResponsesDoNotLeakPayload`,
`TestOverloadReturns429WithRetryAfter`.

## 3. Идентификация

### REQ-200. Обязательное покрытие

Сервис ДОЛЖЕН идентифицировать семнадцать типов: ФИО, дата рождения, место
рождения, гражданство, серия и номер паспорта, орган выдачи, код
подразделения, дата выдачи паспорта, серия и номер водительского
удостоверения, адрес и его компоненты, email, телефон, ИНН, номер карты,
CVV, ПИН, имя держателя карты.

### REQ-201. Независимость от регистра

Идентификация НЕ ДОЛЖНА зависеть от регистра.

### REQ-202. Вариации написания

Сервис ДОЛЖЕН распознавать: разные разделители внутри значения; порядок
компонентов даты `дд.мм.гггг`, `мм.дд.гггг`, `гггг.мм.дд`, `гггг.дд.мм`;
дату, записанную словами; конструкции с разделяющими словами вида
«серия XXXX номер XXXXXX».

### REQ-203. Уровни уверенности

Каждому кандидату ДОЛЖЕН назначаться один из уровней:

| Уровень | Условие назначения |
|---|---|
| `certain` | форма плюс контрольная сумма либо самодостаточная грамматика |
| `strong` | форма плюс явный маркер типа в окрестности |
| `weak` | совпала только форма |
| `denied` | диапазон накрыт подходящим вето |

Уровень ДОЛЖЕН быть воспроизводим: одинаковый вход даёт одинаковый уровень.
Произвольная числовая оценка уверенности использоваться НЕ ДОЛЖНА.

### REQ-204. Повышение по кластеру

Кандидат уровня `weak` ДОЛЖЕН повышаться до `strong`, если в том же
предложении присутствует кандидат уровня `strong` или `certain` другого типа.

В профиле `paranoid` повышение не применяется: там маскируется всё,
совпавшее по форме.

### REQ-205. Контр-правила

Сервис ДОЛЖЕН отличать персональные данные от похожих сведений. Не являются
персональными данными: упоминание публичной персоны в соответствующем
контексте, топоним, образованный от фамилии, адрес и контакты организации.

Контр-правило НЕ ДОЛЖНО срабатывать, если в том же предложении присутствуют
признаки принадлежности данных клиенту. Однофамилец публичной персоны,
помеченный маркером клиента, ДОЛЖЕН защищаться.

### REQ-206. Разрешение перекрытий

Спаны результата НЕ ДОЛЖНЫ пересекаться. При перекрытии кандидатов
предпочтение отдаётся в порядке: больший уровень уверенности, большая длина,
меньший порядковый номер типа, меньшее смещение начала.

Порядок ДОЛЖЕН быть полным: результат не зависит от порядка работы сканеров.

Перекрытия ДОЛЖНЫ разрешаться на полном наборе кандидатов, а список типов
системы-потребителя ДОЛЖЕН применяться к победителям отбора, а не до него.
Разметка текста НЕ ДОЛЖНА зависеть от настройки потребителя: политика решает,
маскируется ли фрагмент, но не то, чем он считается.

Победитель отбора удерживает свои байты и тогда, когда его тип у потребителя
не маскируется. Проигравший кандидат другого типа НЕ ДОЛЖЕН занимать
освободившееся место.

> Требование внесено по дефекту, найденному 22.09.2026 на демонстрационном
> стенде. В тексте «паспорт серия 4509 номер 123456» номер относился к
> паспорту у потребителя с полным списком типов и к адресу — у потребителя,
> где паспорта в списке нет; во втором случае он маскировался как `[АДРЕС_1]`.
> Сокрытие значения выглядело как работа защиты, но держалось на дефекте: тип
> определялся неверно, а потребитель, сознательно отключивший маскирование
> паспорта, получал его скрытым под чужим именем.

### REQ-207. Расширяемость

Добавление типа ПД ДОЛЖНО выполняться добавлением файла сканера и записи в
реестре типов, без изменения движка, транспорта и ядра обработки.
Расширение справочника ДОЛЖНО выполняться добавлением строк в текстовый файл.

## 4. Маскирование

### REQ-300. Границы значения

Спан ДОЛЖЕН покрывать только значение. Служебные слова, маркеры типа и
окружающий текст в спан входить НЕ ДОЛЖНЫ.

Исключение: составной адрес, где сокращения компонентов входят в спан, так
как без них цепочка распадается на несвязные фрагменты.

### REQ-301. Полнота сокрытия

Замена ДОЛЖНА скрывать значение целиком. Оставлять часть символов исходного
значения открытыми НЕ ДОЛЖНА.

### REQ-302. Стратегии

Сервис ДОЛЖЕН поддерживать стратегии `placeholder`, `asterisks`, `token`,
`synthetic`. Стратегия ДОЛЖНА выбираться на уровне потребителя и МОЖЕТ
переопределяться для отдельного типа ПД.

### REQ-303. Нумерация

Одинаковые значения одного типа в пределах запроса ДОЛЖНЫ получать одинаковый
номер и одинаковую замену. Разные значения ДОЛЖНЫ получать разные номера.

### REQ-304. Сохранность окружающего текста

Текст вне спанов ДОЛЖЕН сохраняться побайтово. Нормализация, выполняемая для
поиска, изменять результат НЕ ДОЛЖНА.

## 5. Политика потребителя

### REQ-400. Состав настроек

Для каждого потребителя ДОЛЖНЫ настраиваться: допуск к сервису, перечень
типов ПД, факт маскирования, право демаскирования, стратегия маскирования по
умолчанию и по типам, правила по комбинациям типов, профиль отнесения.

### REQ-401. Комбинации типов

Правило комбинации ДОЛЖНО подавлять маскирование перечисленных типов, если в
тексте отсутствует хотя бы один из требуемых сопутствующих типов.

### REQ-402. Отключение маскирования

Маскирование МОЖЕТ быть отключено для потребителя явной настройкой.
Отключение НЕ ДОЛЖНО происходить автоматически при отказе защитной обработки,
при ошибке конфигурации или при недоступности зависимости.

### REQ-403. Обновление конфигурации

Обновление ДОЛЖНО публиковаться атомарно: читатель видит либо прежний снимок
целиком, либо новый целиком.

Невалидное обновление ДОЛЖНО отклоняться с сохранением действующего снимка.
Отсутствие корректной начальной конфигурации НЕ ДОЛЖНО приводить к обработке
запросов без защиты.

### REQ-404. Изоляция

Соответствия, политика и производные данные ДОЛЖНЫ быть изолированы между
потребителями. Потребитель НЕ ДОЛЖЕН получить доступ к соответствию другого
потребителя и НЕ ДОЛЖЕН разрушить его.

Знание идентификатора корреляции авторизацией не является.

*Приёмка:* `TestProcessIsolatesConsumers`,
`TestProcessForeignConsumerDoesNotClobberRecord`.

## 6. Продуктовый контур

### REQ-500. Аутентификация

Продуктовые эндпоинты ДОЛЖНЫ требовать ключ доступа. Неизвестный ключ и ключ
отключённого потребителя ДОЛЖНЫ приводить к `401` без указания, какая именно
проверка не прошла.

### REQ-501. Точка выпуска наружу

Исходящий запрос в модель МОЖЕТ быть отправлен, только если выполнены все
условия: потребитель аутентифицирован и допущен, детекция завершена без
ошибки, политика применена, все отобранные спаны заменены, соответствие
сохранено.

При невыполнении любого условия запрос отправлен быть НЕ ДОЛЖЕН. Клиент
получает `500` с телом без персональных данных. Ни исходный, ни частично
обработанный текст наружу уходить НЕ ДОЛЖЕН.

*Приёмка:* тест-перехватчик downstream (T-12): поиск по каждому размеченному
значению в фактически отправленном теле; при отказе защиты — ноль отправленных
запросов. Проверка кода ответа и журнала эту проверку не заменяет.

### REQ-502. Восстановление в ответе модели

Восстанавливаться ДОЛЖНЫ только плейсхолдеры, выданные в пределах той же
области корреляции и разрешённые политикой. Неизвестный или подделанный
плейсхолдер раскрывать данные НЕ ДОЛЖЕН.

Ответ модели ДОЛЖЕН проходить идентификацию заново: модель могла породить
персональные данные, отсутствовавшие в запросе.

### REQ-503. Явное маскирование и восстановление

`POST /api/v1/mask` и `POST /api/v1/unmask` ДОЛЖНЫ требовать ключ (REQ-500) и
применять политику потребителя-владельца ключа. Маска ДОЛЖНА выдаваться только
после полной защиты и записи соответствия в область потребителя; при отказе
защиты — `500` без маски и без записи (превышение предела замен — `413`,
REQ-600). `unmask` ДОЛЖЕН отвечать `403`
потребителю без права `demask` и `404` — одинаково на неизвестный, чужой и
истёкший идентификатор. Восстанавливаться ДОЛЖНЫ только плейсхолдеры,
выданные для этого идентификатора (REQ-502).

*Приёмка:* `internal/httpapi/api_test.go` (T-24).

## 7. Ресурсы и устойчивость

### REQ-600. Ограничения входа

Размер тела запроса, число кандидатов, число замен, число и суммарный объём
соответствий ДОЛЖНЫ быть ограничены настройками.

Превышение предела числа замен (`detection.max_spans` или `max_spans`
потребителя) НЕ ДОЛЖНО приводить к частичной маске: значения сверх предела
остались бы в тексте открытыми при внешне успешном ответе (дефект T-52:
20 050 телефонов давали `200`, 20 000 масок и 50 открытых номеров). Движок
сообщает о превышении флагом `detect.Result.LimitExceeded`, ядро —
ошибкой `gateway.ErrSpanLimit`; исход по контурам:

| Контур | Поведение при превышении | Код | Исход в журнале и метриках |
|---|---|---|---|
| `POST /process` | строка скрывается целиком (`[ЗАЩИЩЕНО]`), оригинал записывается в хранилище, обратный шаг возвращает его побайтово | `200` | `degraded` |
| `POST /api/v1/mask` | маска не выдаётся, соответствие не записывается | `413` | `fail_closed` |
| `POST /api/v1/analyze` | боевой путь отказывает без выпуска, частичный разбор не показывается | `413` | `fail_closed` |
| `POST /v1/chat/completions` | запрос в модель не отправляется, соответствие не записывается (REQ-501) | `500` | `fail_closed` |
| ответ модели на прокси | ответ клиенту не отдаётся (REQ-502) | `500` | `fail_closed` |

Для явного API и стенда выбран `413`, а не `500`: превышение — ограничение
входа того же рода, что предел размера тела, повтор того же текста даст тот
же отказ, и клиенту нужно разбить текст, а не повторять запрос. Сообщение
называет только предел из конфигурации. Продуктовый прокси отвечает `500` по
общему правилу fail-closed (AGENTS.md §3). В журнал и метрики значения не
попадают: только потребитель, предел и исход.

*Приёмка:* `internal/detect/engine_test.go` (`TestDetectReportsSpanLimit`,
`TestSelectLimitExceededOnlyForUnmaskedValue`),
`internal/gateway/process_test.go` (`TestProcessSpanLimitDegradesAndRestores`),
`internal/gateway/proxy_test.go` (`TestProxyFailClosedOnSpanLimit`),
`internal/httpapi/api_test.go` (`TestAPIMaskSpanLimitFailClosed`,
`TestAnalyzeSpanLimitFailClosed`) — T-52.

### REQ-601. Срок жизни соответствия

Соответствие ДОЛЖНО удаляться по истечении настраиваемого срока. Истёкшее
соответствие ДОЛЖНО быть недоступно для чтения.

### REQ-602. Перегрузка

При достижении предела одновременной обработки сервис ДОЛЖЕН отвечать `429`
с `Retry-After`, а не накапливать очередь.

### REQ-603. Остановка

Сервис ДОЛЖЕН завершаться корректно: принятые запросы дорабатываются в
пределах настроенного времени, новые не принимаются, фоновые задачи
останавливаются.

### REQ-604. Предел локальной обработки

Детекция, политика, маскирование и запись соответствия ДОЛЖНЫ укладываться в
`server.request_timeout`; ожидание модели в этот предел не входит и
ограничено `llm.timeout`. При исчерпании предела сервис ДОЛЖЕН отвечать `429`
с `Retry-After`: предел выбирается меньше 10 с таймаута проверяющей системы,
и управляемый отказ не приближает остановку прогона (F-13).

Отмена по пределу проверяется не только между сканерами, но и внутри циклов
движка, растущих быстрее числа кандидатов (вето, отбор). На продуктовом
контуре предел передаётся в ядро полем `gateway.ProxyRequest.Budget`, а не
дедлайном общего контекста: дедлайн оборвал бы и ожидание модели. Стенд
`/api/v1/analyze` передаёт остаток предела после диагностического прогона и
отвечает `429` с `Retry-After`, если защита не уложилась до выпуска (T-52).

## 8. Наблюдаемость

### REQ-700. Состав журнала

По каждому запросу ДОЛЖНЫ журналироваться: идентификатор запроса,
идентификатор корреляции, потребитель, операция, перечень выявленных типов ПД,
счётчики по типам, длительность.

*Основание:* ТЗ §3.2.1 прямо требует логирования выявленных типов ПД.

### REQ-701. Запрет на раскрытие

Исходный текст, значения персональных данных, содержимое соответствий, ключи
доступа НЕ ДОЛЖНЫ попадать в журнал, метрики, трассировки, тела ответов об
ошибках и дампы.

*Приёмка:* тест утечек (T-13): поиск по каждому размеченному значению в
журнале, экспозиции метрик и телах ответов.

### REQ-702. Метрики

Сервис ДОЛЖЕН публиковать: распределение времени ответа, число запросов по
исходам, объём обработанного текста в байтах и токенах, счётчики по типам ПД,
состояние хранилища, время ответа модели отдельно от времени сервиса.

Токен для метрики ДОЛЖЕН иметь явно документированное определение. Выдавать
счётчик слов за число токенов модели НЕ ДОЛЖНО.

### REQ-703. Кардинальность меток

Наборы меток метрик ДОЛЖНЫ быть перечислимы. Идентификаторы запросов,
идентификаторы корреляции и текст запроса в метки попадать НЕ ДОЛЖНЫ.

## 9. Целевые показатели

Показатели являются целями приёмки, а не достигнутыми результатами.
Подтверждение — в `PERFORMANCE.md` и `QUALITY.md` после фактических прогонов.

| Показатель | Цель | Условие измерения |
|---|---|---|
| Средняя латентность при 200 соединениях | не более 200 мс для 1000 RPS | только время сервиса, без ожидания модели |
| Латентность по ТЗ | не более 1 с | там же |
| Размер входа | до 100 000 токенов | без отказа и без деградации восстановления |
| Качество обработки | 95% | методика собственная; совместимость с официальным расчётом не подтверждена, см. EXT-01 |
