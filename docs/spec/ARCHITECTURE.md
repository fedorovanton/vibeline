# Архитектура ai-gateway

Документ объясняет устройство системы и основания выбора. Нормативное
описание поведения — в [SPEC.md](SPEC.md), решения и их цена — в
[DECISIONS.md](DECISIONS.md).

## 1. Место в цепочке

Схема: [docs/diagrams/architecture.svg](../diagrams/architecture.svg)
(исходник — `architecture.html` там же), настройки —
[docs/diagrams/settings.svg](../diagrams/settings.svg).

```
                     ┌──────────────────────── граница доверия ────────────────────────┐
                     │                                                                 │
  потребитель ──────►│ httpapi ──► lex + detect ──► policy ──► mask ──► store          │
  (/process без      │ (ключ →                                          │              │
   ключа, /v1/*,     │  потребитель)                    ┌───────────────┤              │
   /api/v1/* с       │                                  ▼               │ /process,    │
   ключом)           │                             internal/llm         │ /api/v1/*:   │
                     │                           (точка выпуска)        │ без модели   │
                     │                                  │               ▼              │
  потребитель ◄──────│◄──────────────────── демаскирование ◄────────────┘              │
                     │                                  ▲                              │
                     └──────────────────────────────────┼──────────────────────────────┘
                                                        │ только маска   ▲ ответ модели
                                                        ▼                │
                                                   LLM AlfaGen ──────────┘
```

Порядок в коде (`gateway.Service.Mask`): разметка лексером, детекция с
профилем потребителя, фильтр политики (типы, комбинации), применение замен
стратегией потребителя; затем запись соответствия в `Store` — до ответа
клиенту и до обращения к модели.

Внутри границы доверия текст существует в исходном виде. Наружу — в модель,
в журнал, в метрики, в тела ошибок — попадает только результат разрешённых
преобразований. Точка выпуска в модель одна, и её предусловия перечислены
явно в коде.

## 2. Состав модулей

| Пакет | Ответственность | Состояние |
|---|---|---|
| `cmd/ai-gateway` | запуск, флаги, сигналы, корректная остановка | владеет всем |
| `internal/config` | схема, разбор, проверка, атомарная публикация снимка | снимок за `atomic.Pointer` |
| `internal/httpapi` | транспорт: разбор запроса, выбор потребителя, коды ответов | без состояния |
| `internal/gateway` | оркестрация обработки, автомат `/process`, инвариант выпуска | пул рабочих областей |
| `internal/policy` | политика потребителя: допуск, типы, стратегия, комбинации | неизменяемо |
| `internal/detect` | идентификация ПД: сканеры, контекст, разрешение перекрытий | неизменяемо |
| `internal/lex` | однопроходная разметка текста | буферы запроса |
| `internal/mask` | стратегии замены и применение спанов | буферы запроса |
| `internal/store` | соответствия «идентификатор → оригинал и маска» | шардированная память |
| `internal/llm` | клиент downstream-модели | переиспользуемый клиент |
| `internal/obs` | журнал и метрики | атомарные счётчики |

Зависимости направлены в одну сторону: транспорт знает про ядро, ядро — про
детекцию, маскирование и хранилище, детекция не знает ни про кого. Обратных
зависимостей нет, поэтому поведение ядра проверяется без поднятия сети.

## 3. Ключевые решения

### 3.1. Сначала разметка, потом преобразование

Анализаторы не изменяют текст. Они возвращают спаны — байтовые диапазоны с
типом и уровнем уверенности. Политика решает, какие спаны маскировать.
Только после этого собирается результат.

Причина: без разделения невозможно ни объяснить решение, ни показать его в
демо, ни применить политику потребителя к уже изменённому тексту.

### 3.2. Нормализованная копия, выровненная с оригиналом

Лексер строит нормализованную копию текста: нижний регистр и «ё» → «е».
Для кириллицы и латиницы такое преобразование не меняет длину в UTF-8,
поэтому смещения в копии совпадают со смещениями в оригинале. Руны, у
которых нижний регистр занимает другое число байт, копируются без изменения.

Что это даёт: сканеры сравниваются со справочниками по нормализованной форме
и сразу получают корректные смещения в исходном тексте. Требование ТЗ о
независимости от регистра выполняется без пересчёта позиций — а пересчёт
позиций как раз и является типичным источником ошибок на кириллице.

Цена: одна аллокация размером со вход на запрос, снимаемая переиспользованием
буфера из пула.

### 3.3. Уровень уверенности вместо score

Кандидат получает один из четырёх уровней: `certain` — форма плюс контрольная
сумма, `strong` — форма плюс явный маркер типа, `weak` — только форма,
`denied` — сработало контр-правило.

Это перечисление условий, а не вероятность. Произвольный score нельзя
объяснить жюри, нельзя воспроизвести и нельзя откалибровать без размеченных
данных, которых нет.

### 3.4. Кластеризация по предложению

Слабый кандидат повышается до сильного, если в том же предложении есть
достоверное значение другого типа. Три цифры сами по себе ничего не значат,
но три цифры рядом с номером карты, прошедшим проверку Луна, — это CVV.

Тот же механизм закрывает требование ТЗ §6 о маскировании по комбинации
типов: правило «ПИН только вместе с картой» выражается параметром, а не
отдельной веткой кода.

### 3.5. Контр-правила выражаются запретом

Сканеры независимы и не знают о находках друг друга. Правило «поэт Пушкин —
не персональные данные» регистрирует не отсутствие кандидата, а запрет на
диапазон. Движок сопоставляет запреты с находками.

Иначе правило пришлось бы дублировать внутри каждого сканера, а добавление
нового сканера молча теряло бы часть контр-правил.

### 3.6. Маскирование — чистая функция

Результат зависит только от текста и политики. Номер плейсхолдера
определяется порядком первого появления значения.

Три следствия, каждое из которых иначе потребовало бы отдельного механизма:
повтор прямого шага возвращает ту же маску без обращения к состоянию;
параллельные повторы с одним идентификатором безвредны, поэтому не нужен
singleflight; одинаковые значения получают одинаковый плейсхолдер, и
замаскированный текст остаётся связным для модели.

### 3.7. Направление определяется состоянием, а не счётчиком

Контракт автопроверки не содержит поля операции. Направление выводится
сопоставлением входа с сохранённым состоянием по идентификатору.

Счётчик вызовов здесь не работает: проверяющая система повторяет запрос при
ошибке и при 429, и второй вызов не обязан быть обратным шагом. Таблица
переходов — в [SPEC.md](SPEC.md).

### 3.8. Разное поведение при отказе в разных контурах

В продуктовом прокси действует строгий fail-closed: при любом отказе защиты
запрос в модель не отправляется, клиент получает ошибку. Доступность не
оправдывает раскрытие данных.

В контракте автопроверки отказ обрабатывается иначе: текст скрывается
целиком. Причина внешняя — пять невалидных ответов подряд останавливают весь
нагрузочный прогон. Избыточная маска стоит штрафа по одному элементу,
оборванный прогон стоит всей оценки. Утечки при этом не происходит.

### 3.9. Один бинарник, хранилище в памяти

Соответствия живут в шардированной памяти процесса за интерфейсом `Store`.
Внешнее хранилище в контуре прогона добавило бы латентность и точку отказа,
не дав ничего взамен: прогон длится пять минут, а восстановление нужно
только между двумя запросами одной пары.

Цена зафиксирована честно: при рестарте соответствия теряются, между
репликами память не разделяется. Интерфейс выделен под реальную заменяемую
зависимость, поэтому подключение Redis не потребует правки вызывающего кода.

## 4. Модель угроз

| Угроза | Механизм защиты | Чем проверяется |
|---|---|---|
| Незамаскированные ПД уходят в модель | Единственная точка выпуска с явными предусловиями; при отказе — ноль исходящих запросов | Тест-перехватчик downstream: поиск по каждому размеченному значению в фактически отправленном теле |
| ПД попадают в журнал или метрики | В журнал идут типы и счётчики, значений нет; метки метрик перечислимы по построению | Тест утечек: поиск по каждому значению в журнале, `/metrics` и телах ответов |
| Раскрытие по известному идентификатору | Идентификатор корреляции не является авторизацией: проверяется разрешение потребителя | Тест демаскирования без права |
| Доступ к чужим соответствиям | Ключ хранилища включает область потребителя | Тест изоляции и тест на неразрушение чужой записи |
| Подделанный плейсхолдер | Восстанавливаются только плейсхолдеры, выданные в разрешённой области | Тест подделки |
| Исчерпание памяти | Лимиты по числу записей и по объёму, вытеснение, TTL, ограничение размера входа | Тест лимитов, нагрузочный прогон |
| Перегрузка | Предел одновременной обработки, 429 с `Retry-After` вместо растущей очереди | Тест перегрузки |
| Утечка ключа модели | Ключ только в переменной окружения из `.env`; в конфигурации — имя переменной | Проверка архива при сборке |
| Чтение соответствий из памяти процесса | Не защищено шифрованием: память процесса — доверенная зона; соответствия не покидают процесс, живут до TTL; профилировщик слушает только петлевой адрес | Решение и цена — `DECISIONS.md` §4 |

## 5. Развёртывание

Один контейнер без оболочки и пакетного менеджера, непривилегированный
пользователь, статический бинарник. Конфигурация монтируется снаружи и
перечитывается по сигналу без простоя; невалидное обновление отклоняется,
и сервис продолжает работать на прежнем снимке.

Предел памяти контейнера задаётся явно и должен превышать лимит хранилища
с запасом на рабочие буферы. Готовность и живость проверяются отдельными
эндпоинтами; бинарник умеет проверять сам себя, поскольку в образе нет curl.

Kubernetes не рассматривается: производственная готовность не оценивается,
а запуск нескольких реплик сам по себе масштабирование не доказывает —
при хранилище в памяти он ещё и разрушил бы корреляцию.

## 6. Что ограничивает пропускную способность

Проверяющая система работает закрытым контуром: до 200 соединений, каждое
ждёт ответа перед отправкой следующего запроса. Отсюда пропускная
способность равна `соединения / средняя латентность`, и выше этого значения
выдать невозможно — ограничивает конкурентность клиента, а не ёмкость сервиса.

| Целевой RPS | Требуемая средняя латентность |
|---|---|
| 330 — средний уровень прогона | не более 600 мс |
| 1000 — пик | не более 200 мс |
| 2000 — бонус ТЗ §6 | не более 100 мс |

Проектные следствия: регулярные выражения в горячем пути не используются,
сканеры работают по токенам единственной разметки, справочники и правила —
общий неизменяемый снимок, буферы переиспользуются, аллокации в ядре
удерживаются около нуля. Замеренные значения — в `PERFORMANCE.md` после
прогона; до него любые числа являются целью, а не результатом.
