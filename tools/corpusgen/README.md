# corpusgen — независимый размеченный корпус

Инструмент порождает синтетический корпус для оценки качества детекции
персональных данных: precision, recall, F1 по типам, доля избыточного
маскирования, число ложных срабатываний на ловушках.

## Почему отдельный модуль

Корпус намеренно **не** использует грамматики и справочники детектора. У
`corpusgen` собственный `go.mod`, собственные словари значений (`corpus/vocab.go`),
собственные форматтеры (`corpus/format.go`) и собственные шаблоны предложений
(`corpus/templates.go`, `corpus/traps.go`). Модуль не импортирует `ai-gateway` и
не зависит ни от чего, кроме стандартной библиотеки; это сторожится тестом
`TestNoGatewayImports`.

Причина в методике измерений (`docs/spec/ACCEPTANCE.md` §4): корпус, производный
от детектора, измеряет совпадение кода с самим собой, а не качество, и вся
отчётность на нём становится бессмысленной.

## Запуск

```bash
go run . -out corpus.jsonl            # 1200 коротких записей + 4 длинные, ~4.9 МБ
go run . -out corpus.jsonl -count 400 -long=false
go run . -out - -quiet -count 20      # в стандартный вывод
```

| Флаг | Значение |
|---|---|
| `-out` | файл вывода в формате JSON Lines; `-` — стандартный вывод |
| `-count` | базовое число записей без длинных (по умолчанию 1200) |
| `-seed` | зерно генератора (по умолчанию 20260922) |
| `-long` | добавлять длинные записи на 50 000 и 100 000 токенов (по умолчанию да) |
| `-quiet` | не печатать сводку в поток ошибок |

Один seed даёт **побайтово одинаковый** корпус: без этого метрики разных
прогонов несравнимы. Отчёт качества обязан фиксировать seed и `-count`.

Если при заданном `-count` какой-то тип ПД не набирает 60 записей, генератор
добавляет записи сверх `-count`, пока минимум не выполнен.

## Формат

Одна запись на строку:

```json
{"id":"c-0001","kind":"multi","text":"Найди клиента Иванова Ивана Ивановича, паспорт 4509 123456, и покажи его адрес.","spans":[{"start":26,"end":70,"type":"full_name","value":"Иванова Ивана Ивановича"},{"start":87,"end":98,"type":"passport_number","value":"4509 123456"}],"traps":[]}
```

- `kind` — `single`, `multi`, `trap`, `clean`, `namesake`, `long`.
- `spans` — персональные данные, которые обязаны быть замаскированы.
- `traps` — фрагменты, похожие на ПД, но ПД не являющиеся: маскировать их не
  надо, по ним считаются ложные срабатывания. `type` — тип, за который фрагмент
  можно ошибочно принять, `reason` — почему это не ПД (`public_figure`,
  `toponym`, `org_address`, `hotline`, `contract_number`, `event_date`).
- `value` продублировано рядом со смещениями: по нему удобно искать утечку в
  фактически отправленном в модель теле (`AGENTS.md` §9).

**Смещения байтовые** и полуинтервальные: `text[start:end] == value`. Кириллица
занимает два байта, поэтому смещение не равно номеру символа. Проверяется
тестами `TestSpanOffsetsAreBytes` и `TestCyrillicOffsetsExplicit`.

## Соглашения о границах спанов

Границы идут ровно по значению: служебные слова в спан не входят, потому что их
маскирование штрафуется как избыточное (`07-clarifications.md` §7.1).

- «серия 4509 номер 123456» → **два** спана `passport_number`: `4509` и `123456`;
  слова «серия» и «номер» остаются снаружи. То же для водительского удостоверения.
- «12 марта 1987 года» → спан `12 марта 1987`, слово «года» снаружи.
- Адрес размечается целиком одним спаном, включая индекс, регион и «г. …»:
  дробление оставило бы часть значения открытой, а полное сокрытие
  предпочтительнее частичного.
- Место рождения размечается без родового слова: «в городе Ирбит» → спан `Ирбит`.

## Синтетика

Все значения синтетические. Номера карт собираются из тестовых BIN и получают
корректную контрольную цифру Луна; ИНН — с верными контрольными разрядами;
почта — только в зарезервированных RFC 2606 доменах `example.*`. Публичные
персоны и топонимы (Пушкин, улица Пушкина) встречаются только в ловушках и в
записях об однофамильцах, где по условию задачи и должны быть.
